# QA acceptance walkthrough

Step-by-step instructions for every row of [QA-ACCEPTANCE.md](QA-ACCEPTANCE.md), against your `QA-Annotation.xlsm`. Do these in order — several later tests depend on data an earlier test created (the entities from test 3 are reused in tests 4, 5, 8, 9, 11).

Record, for every row: pass/fail, the exact message text if one appeared, and Excel version/bitness/AutoSave state (per QA-ACCEPTANCE.md's own instructions).

## 0. Naming conventions — read this first

**Note import files.** Name is exactly `CLAIM_NUMBER_NOTEID.txt`, split on the **last** underscore — so a claim number itself must never contain an underscore. `C201_N01.txt` → claim `C201`, note `N01`. UTF-8 only.

**Sheet tabs**, left to right, exactly as spelled (case doesn't matter to Excel, but match the words): `Review Desk`, `Notes`, `AI Instructions`, `AI Analysis Input`, `AI Queue`, `Watchlist Desk`, `Instructions`, then the backend tables: `Note Register`, `Note Parts`, `Queue Store`, `Recent AI Analysis`, `Runs`, `Entries`, `Drafts`, `Legacy Archive`, `State`, `Decisions`, `Entities`, `Mentions`, `Fields`, `Context`, `Statements`, `Uncertain`, `Raw Client Output`, `Watchlist Review`. 25 sheets total.

Two names are easy to confuse: **`AI Queue`** is where you or Copilot write draft proposals (table `tInput`, headers on row 5). **`Queue Store`** is a separate sheet the workbench manages for you (table `tQueue`) — never type into it by hand.

**Buttons**, caption → what it runs, so a QA note can name the click precisely:

| Sheet | Caption | Runs |
|---|---|---|
| Review Desk | Select note | `SelectNote` |
| Review Desk | New manual entry | `NewEntry` |
| Review Desk | Load next AI draft | `LoadNextCandidate` |
| Review Desk | Attest & Save | `AttestSave` |
| Review Desk | Save draft | `SaveDraft` |
| Review Desk | Resume saved draft | `ResumeDraft` |
| Review Desk | Previous entry / Next reviewed entry | `PreviousEntry` / `NextEntry` |
| Review Desk | Delete entry | `DeleteEntry` |
| Review Desk | Choose entity | `ChooseEntity` |
| Review Desk | Locate evidence | `LocateEvidence` |
| Review Desk | Complete note | `CompleteNote` |
| Review Desk | Previous/Next text page | `PreviousTextPage` / `NextTextPage` |
| Review Desk | Watchlist review | `OpenWatchlist` |
| Notes | Paste whole note / Import TXT files / Open selected note | `PasteWholeNote` / `ImportNotes` / `OpenSelectedNote` |
| AI Analysis Input | Save queue snapshot | `SaveQueueSnapshot` |
| Watchlist Desk | Load next pair / Save decision / Import client output | `LoadWatchlistMatches` / `SaveWatchlistDecision` / `ImportClientOutput` |

**Review Desk form cells**, since you'll type into these constantly: C4 claim number, C5 note ID, C6 source version, C7 reviewer, C9 entry kind, C10 exact source quote, C11 occurrence, C12 entity reference, C13 display name, C14 entity type, C15 reference form, C16 field kind, C17 field value, C18 second entity, C19 open label, C20 context/reason.

**Test data.** Real fictional data lives in `sample-data/`. `stress-packet/notes/` has all 60 files the packet test needs, claims `C201`–`C206`, 10 notes each, with a matching `stress-packet/client-export.csv` covering the same 6 claims. `C104_N01.txt`/`C104_N02.txt` sit one level up. Six more files exist only for this walkthrough, generated by `generate_qa_test_notes.py` into `sample-data/qa-test-notes/`, claim `QA01` (chosen so it can't collide with any real claim number): `QA01_N01.txt` (32,766 units), `N02` (32,767), `N03` (32,768), `N04` (100,000), `N05` (the emoji/CRLF/combining-accent/part-boundary note), `N06` (the two-John ambiguous-pronoun note). Regenerate them any time with `python generate_qa_test_notes.py`; the printed stats and this document are kept in sync.

## 1. Setup twice, save under another name and setup again

1. Alt+F8 → `SetupWorkbench` → Run. Confirm one shape per row of the button table above — no duplicates.
2. File → Save As → a **different** filename, still `.xlsm` (e.g. `QA-Annotation-2.xlsm`).
3. Alt+F8 → `SetupWorkbench` → Run again in the new copy.
4. Click every button once from a clean state to confirm each still fires only its own macro (no cross-wiring). `Button()` deletes-then-recreates its own shape by name (`wb_<macro>`), so re-running Setup must not leave two shapes stacked on the same spot — right-click empty space near any button and confirm only one shape is selectable there.
5. No merged cells: select the full `Review Desk` sheet (Ctrl+A) and check **Home → Merge & Center** is not highlighted/active.

## 2. With no Copilot, import the 60-note fictional packet

1. `Notes` sheet → **Import TXT files**.
2. Navigate to `sample-data/stress-packet/notes/`, select all 60 files (Ctrl+A in the dialog), Open.
3. Expect the message *"Imported 60 notes. Check their reading order in Note Register before reviewing."*
4. Open `Note Register`. Confirm 60 rows, `status` = `in_progress` for all, `claim_number` spanning `C201`–`C206`.
5. **Reading order is not inferred from claim** — `note_order` is assigned globally across the whole selection (file 1 you picked gets order 1, file 2 gets order 2, …), not restarted per claim. Column D (`note_order`) is deliberately left unlocked so you can correct it by hand per claim; that's what "reading order editable" in the expected result means. Fix it now for at least one claim before moving on.
6. Full source text: pick one row, note its `source_id`, then confirm on `Note Parts` that the rows with that `source_id` concatenate back to the original `.txt` file's exact content.

## 3. First note, first word: Dr. Ada Monroe

1. `Note Register` → click a row for `C104` / `N01` (or any note whose text starts with a name) → **Open selected note** (also on the `Notes` sheet, or column J's button on `Note Register` itself).
2. On `Review Desk`: C9 `entity`, C10 `Dr. Ada Monroe`, C11 `1`, C13 `Dr. Ada Monroe`, C14 `person`, C7 your reviewer name.
3. **Attest & Save.**
4. Expect: attestation dialog quoting the C24 text, then *"Saved revision 1: A1"* (or similar `A#`). Check `Entries`: `start_character` = `0` (0-based code-point offset) for this occurrence, `action` = `entity`, `state` = `accepted`. Check `Entities`: one new row, `entity_ref` = `E1` (or the next unused `E#`).

## 4. Same quote, occurrence 2

1. Same note still open. C9 `reference`, C10 `Dr. Ada Monroe`, C11 `2`, C12 = the `E#` from test 3 (use **Choose entity** rather than typing it), C15 `name`.
2. **Attest & Save.**
3. Expect a *different* `start_character`/`end_character` than test 3's entry, and `entity_ref` on `Mentions` pointing at the *same* `E#` — not a second `Entities` row. If your note's second occurrence of that exact phrase doesn't exist, use **Locate evidence** first to confirm the occurrence count before saving.

## 5. Save address, TIN, context, statement and uncertain text

Do all five kinds against the same open note, each its own **New manual entry** → fill → **Attest & Save**:

| Kind | C9 | C16/C17 or C20 | Check afterward |
|---|---|---|---|
| Address | `field` | C16 `address`, C17 the literal address text | `Fields` row, `value` exact |
| TIN | `field` | C16 `TIN`, C17 the TIN **as written, including leading zeros** | `Fields` row — confirm the leading zero survived (it's stored `NumberFormat "@"`, so it must) |
| Context | `context` | C20 optional label | `Context` row |
| Statement | `statement` | C12 the entity, C20 free text | `Statements` row |
| Uncertain | `uncertain` | C20 **required** — why it can't be resolved | `Uncertain` row |

All five should locate on **Locate evidence** before you save each one.

## 6. Same name for two people / ambiguous pronoun

1. Import `sample-data/qa-test-notes/QA01_N06.txt` (claim `QA01`, note `N06`) via **Import TXT files**, then open it.
2. Create **two separate entities**: `John Carter` and `John Reyes` (two `New manual entry` → C9 `entity` → **Attest & Save**, once each). Confirm two distinct `E#` values in `Entities`, not one.
3. For the ambiguous `He`: C9 `reference`, C10 `He`, C11 `1`. You as reviewer must pick — either C12 = whichever John the surrounding text actually supports, with C15 `pronoun`, **or** C9 `uncertain` with C20 explaining the ambiguity. Confirm the workbench does **not** auto-resolve this for you; nothing should let you save a reference with no entity chosen and no uncertainty explanation (leave C12 blank, C9 `reference`, and Attest & Save should refuse it).

## 7. Manual draft, save, close/reopen, Resume saved draft

1. **New manual entry**, fill in something plausible, but click **Save draft** instead of Attest & Save.
2. Expect *"Draft saved. It is not an accepted annotation."* Confirm a new row on `Drafts`.
3. Close the workbook entirely (this exercises `Workbook_BeforeClose` — if you skipped pasting `ThisWorkbook.txt`, this whole test is meaningless since nothing will guard the close). Reopen it.
4. On `Review Desk`, click **Resume saved draft**. Expect an input box listing your draft by its action/quote. Enter its position number.
5. Confirm the form refills with exactly what you typed before closing, and the status line reads *"Resumed draft; not attested."* It must still require a fresh **Attest & Save** — resuming does not accept it.

## 8. Edit accepted entry; Previous; Cancel / discard / save draft

1. Load the entity you accepted in test 3 (**Previous entry** / **Next reviewed entry** navigate accepted entries by evidence position; or note its `A#` and use `LoadEntry` indirectly by browsing).
2. Change C14 (entity type) to something else, then click **Previous entry** *without saving first*.
3. Expect a prompt: *"Unsaved changes: Yes = save draft; No = discard edits; Cancel = stay here."*
   - **Cancel** → form must still show your edited value, unmoved.
   - **No** → form reverts to the last saved value, then navigates.
   - **Yes** → saves a draft (not an acceptance — check `Drafts`, not a new `Entries` revision), then navigates.
4. Reload that same entry (`LoadEntry`) and confirm the **accepted** record in `Entries` is unchanged — your edit only became real once you separately ran **Attest & Save** on it.

## 9. Double click acceptance; save same unchanged revision again

1. Load an accepted entry, change nothing, click **Attest & Save** twice in a row without editing between clicks.
2. First click: expect *"This revision is already saved."* with no dialog to attest (the code short-circuits before the attestation prompt when the form isn't dirty and the entry is already accepted).
3. Confirm `Entries` still has exactly one accepted row for that `A#` at the same revision number — no duplicate row, no revision bump.

## 10. Delete entity with accepted dependents

1. Take the entity from test 3 (which now has a `reference` in test 4 and probably a `statement`/`field` depending on it).
2. Load that entity's own entry, click **Delete entry**.
3. Expect: *"This entity has accepted dependents. Reassign them first."* — deletion is blocked, not silently allowed.
4. Confirm no row was removed or retired on `Entries`.
5. To see the *positive* delete path: create a throwaway entity with nothing depending on it, delete it, confirm `Entries` gains a `retired` row (history preserved) rather than the row vanishing, and `Entities`/`Mentions` output stays consistent (`RebuildOutputs` reruns).

## 11. Queue snapshot; load, correct, accept; return to entry

Use `sample-data/qa-test-notes/QA01_N05.txt` or any already-imported note. No Copilot needed for this test — you're hand-typing what Copilot would normally write, to isolate the queue mechanics from the model.

1. Open the note. On `AI Analysis Input`: C4 a run label (e.g. `manual-test-1`), C5 processed parts (e.g. `1`), C6 `no`, C7 a brief note.
2. On `AI Queue`, row 6 (row 5 is the header — never overwrite it): candidate_key `R1`, action `entity`, source_quote a real exact phrase from the note, occurrence `1`, entity_key `P1`, display_name anything, entity_type `person`.
3. **Save queue snapshot.** Confirm the dialog, expect *"Queue snapshot saved. Load next AI draft on Review Desk…"*. Check `Queue Store` for a new row with `status` = `pending` (or `needs_attention` if the quote didn't locate).
4. `Review Desk` → **Load next AI draft**. The form fills from the queue row.
5. **Deliberately correct something** before accepting — e.g. change C13's display name to something different from what you staged.
6. **Attest & Save.** Confirm `Entries` shows **your corrected value**, not the original staged `display_name` — this is the exact behavior QA-ACCEPTANCE.md is checking ("Latest SME edits appear, not the original AI wording").
7. Confirm `Queue Store`'s row for `R1` now shows `status` = `accepted` and `entry_id` populated with your new `A#`.

## 12. Snapshot identical queue twice

1. Without changing anything on `AI Queue` or `AI Analysis Input` from test 11's staged row, click **Save queue snapshot** a second time.
2. A new physical row is always added to `Queue Store` on every snapshot — nothing suppresses that. What matters is its `status`: because this candidate's fields exactly match the one you already resolved in test 11, the duplicate check copies the *existing* row's status and `entry_id` onto the new row rather than staging it fresh — so the new row reads `status` = `accepted` with the same `entry_id` as test 11, **not** `pending`. (The literal status `duplicate` is reserved for staging the same *unresolved* candidate twice in a row — a `pending`/`needs_attention` row snapshotted again before it's ever been loaded — which is a different case from this one.) Either way, `LoadNextCandidate` only pulls `pending`/`needs_attention` rows, so this candidate does not resurface for reprocessing.
3. Confirm the accepted `Entries` row from test 11 is untouched.

## 13. Wrong note quote, repeated quote, blank occurrence, unresolved draft entity key

Four separate save attempts, each expected to fail with its own message:

1. **Wrong note quote** — copy an exact phrase from a *different* note's text, paste it into C10 on the *current* note, Attest & Save → *"Exact evidence was not found at this occurrence. Use Locate evidence."*
2. **Repeated quote** — reuse a `source_quote` + `occurrence` combination you've already accepted for the *same* action/entity/field combination on a *new* entry (don't edit the existing one, start fresh with New manual entry) → *"This annotation already exists. Use Previous/Next reviewed entry to revise it."*
3. **Blank occurrence** — clear C11 entirely, Attest & Save → *"Occurrence must be a positive whole number."*
4. **Unresolved draft entity key** — type a raw draft-style key like `P9` directly into C12 (skip **Choose entity**), pick `reference` or `field` for C9, Attest & Save → *"Choose an accepted entity. A local AI key is not an accepted entity reference."*

## 14. Formula in queue/form, formula-like literal note

1. **Formula in the AI Queue**: on `AI Queue` row 6, type `=1+1` into the `source_quote` cell. **Save queue snapshot** → *"AI Queue contains formulas. Replace them with literal values."*
2. **Formula in the form**: on `Review Desk` C10, type `=SUM(1,1)`. **Attest & Save** → *"Use literal text in the annotation form, not formulas."*
3. **Formula-like literal note**: create a plain-text file containing only `=1+1` as its body, name it e.g. `QA01_N07.txt`, import it, open it. Confirm the note displays as the literal text `=1+1` (not a computed `2`) everywhere it's shown — `Review Desk` G-column preview, `Note Parts`. Every cell the workbench writes to is forced to text format (`NumberFormat "@"`) before the value is written, specifically so this can't turn into a live formula.

## 15. Long notes at 32,766 / 32,767 / 32,768 / 100,000+ units

1. Import `QA01_N01.txt` through `QA01_N04.txt` (32,766 / 32,767 / 32,768 / 100,000 units respectively).
2. For each: open it, confirm on `Note Register` that `length_utf16` matches exactly. Open selected note and confirm the G-column preview's *first* page starts `FIRST-<n>-` and, after paging through with **Next text page** to the end, the *last* page ends `-LAST-<n>` with no truncation or corruption at any 8,000-unit part boundary in between.
3. This exercises `SafeTake`'s chunking at exactly the point Excel's own classic 32,767-character single-cell limit would bite if the code ever put a whole note in one cell — it doesn't, since it's split into `Note Parts` rows of at most 8,000 units each, so all four sizes should behave identically.

## 16. Emoji at split point, CRLF, combining accents, quote crossing part boundary

1. Import and open `QA01_N05.txt`. It's built to straddle the 8,000-unit part boundary on purpose: `STRADDLEBOUNDARY` (an exact 17-character literal) starts at UTF-16 unit 7,991 and ends at 8,007 — meaning it's split across two different `Note Parts` rows on disk.
2. On `Review Desk`, C10 `STRADDLEBOUNDARY`, C11 `1`, **Locate evidence**. It must be found and highlighted correctly even though no single stored part contains the whole word.
3. Immediately after it come a 😀 emoji (a surrogate pair — 2 UTF-16 units), then `é` written as base `e` + a combining acute accent (2 separate code points, not the single precomposed character), then a CRLF, then `TAIL-MARKER-END`. Confirm all of that survives round-trip in the text preview exactly as written — no dropped combining mark, no CRLF collapsed to LF, no half-emoji.

## 17. Sixth distinct note paste, old pending queue

`Recent AI Analysis` only ever gets rows from a **queue snapshot** (`ArchiveAnalysis` is called solely from `SaveQueueSnapshot`) — capturing a note's text, whether by paste or TXT import, never writes to it directly. So there's nothing to prune unless you first put something there.

1. Note **A**: open it, stage anything on `AI Queue` (candidate_key, action, source_quote, occurrence — same as test 11), **Save queue snapshot**. Confirm `Recent AI Analysis` now has rows for A. Leave one candidate from this snapshot unresolved so A also has a `pending` row on `Queue Store`.
2. Capture five *more* distinct notes, B through F — paste or TXT import, either works identically here, since what actually drives retention is `paste_sequence` on `Note Register`, bumped by capture (`CaptureNote`) regardless of path.
3. Note Register now shows six distinct `claim_number`+`note_id` keys touched, with A the least recently touched of the six. `PruneAnalysis` runs at the end of every capture, so after F is captured, A drops out of the 5 most-recently-touched set.
4. Confirm `Recent AI Analysis` no longer has any rows for A, while B–F's (whichever of them had any) remain. Confirm A's `Note Register`/`Note Parts` rows are completely untouched, and A's `pending` `Queue Store` row from step 1 is **still there** — pruning only ever touches `Recent AI Analysis`.

## 18. Re-paste same note unchanged / changed

1. Open a note you've already imported. Copy its exact original text again and **Paste whole note** with the same claim/note ID/order in C4/C5/C6.
2. Unchanged text: confirm it silently reuses the same `source_id` — no new `Note Register` row, `version` unchanged.
3. Now change the text slightly (add a sentence) and paste again with the same claim/note ID. Expect: *"This note's text changed. Keep the old version and create a new review version?"* → Yes → confirm a **new** `Note Register` row with `version` incremented, the old row's `status` set to `superseded`, and every entry/mention you'd already accepted against the old version still pointing at its original `start_character`/`end_character` (unshifted).

## 19. All AI proposals done but manual draft remains

1. On a note with at least one `pending`/`needs_attention` `Queue Store` row, resolve every one of them (accept or dismiss via **Delete entry**) so none remain unresolved for that note.
2. Leave one **Save draft** sitting unresolved for that same note (don't Attest & Save it, don't delete it).
3. **Complete note.** Expect: *"Resume and resolve saved drafts before completing the note."* — completion is blocked even though the AI queue itself is fully resolved.
4. Resume the draft (**Resume saved draft**), either save it for real (**Attest & Save**) or discard it, then **Complete note** again — should now succeed, showing the completeness attestation prompt.

## 20. Zero entities / reviewed uncertainty

1. Import a fresh short note. Add only **one** `uncertain` entry covering some piece of text, with a real C20 explanation — create **zero** `entity` rows for this note.
2. **Complete note.** Confirm it's allowed to succeed (assuming no other pending queue rows or drafts) — the workbench must not require at least one entity to exist before a note can be marked complete.

## 21. InjectNextSaveFailure, then try an entry save

1. Alt+F8 → `InjectNextSaveFailure` → Run. Expect *"Pre-save failure injection is ON. Use only in a disposable QA copy."* — confirm you're in `QA-Annotation.xlsm`, not a real workbook, before doing this.
2. Attempt a normal entry: **New manual entry**, fill it in, **Attest & Save**, confirm the attestation dialog.
3. Expect a message box titled **"Not saved"** starting *"Injected pre-save failure."* Confirm: no new row in `Entries`, no `Queue Store` status change, and the form still shows exactly what you typed (nothing was cleared).
4. Alt+F8 → `InjectNextSaveFailure` → Run again to toggle it back **OFF** — confirm the message now says *"…is OFF."*
5. Redo the same save. It should now succeed normally.

## 22. Read-only file, unavailable save destination

1. Close `QA-Annotation.xlsm`. In File Explorer, right-click it → Properties → check **Read-only** → OK. Reopen it in Excel (Excel will likely show "[Read-Only]" in the title bar).
2. Attempt any save action (**Attest & Save** on a fresh entry). Expect it to fail cleanly with *"Save a writable .xlsm working copy first."* rather than appearing to succeed. Confirm nothing changed in any table.
3. Undo the read-only flag (uncheck it in Properties) before continuing.
4. For "unavailable save destination": move or rename the folder the `.xlsm` lives in while Excel still has it open (simulating a lost network drive), then attempt a save. Confirm the same class of clean failure — no silent success, no partial write.

## 23. Client import missing header / malformed CSV

1. Take a copy of `sample-data/client-export.csv`, delete one column entirely (e.g. `entity_TIN`), save it as `bad-missing-header.csv`.
2. `Watchlist Desk` → **Import client output** → select it. Expect *"Missing client column: entity_TIN"* (or whichever column you removed) — import refused outright.
3. Take another copy, break the CSV structure deliberately — e.g. add an extra unescaped comma in one data row so it has a different field count than the header row. Import it. Expect *"CSV row N has a different number of fields."*
4. After both failed attempts, confirm `Raw Client Output` is completely unchanged from before you tried — a rejected import must not partially land.

## 24. Watchlist metadata conflicts / no numeric score

1. **Import client output** using `sample-data/stress-packet/client-export.csv` (all columns present, matches all 26 required headers).
2. Complete a note for one of `C201`–`C206` first (watchlist review is blocked pre-completion — see `OpenWatchlist`'s own check).
3. **Watchlist review** → **Load next pair**. Confirm every available client-side field renders in the G-column pair display, including rows where `GenAI_tok_sort_similarity` is blank/non-numeric — the display must not choke or hide the row just because a score is missing.
4. Set C5 (identity decision) to `insufficient_evidence`, C6 a reason, C7 (reviewer) filled, **Save decision**. Confirm it's accepted — `insufficient_evidence` must be a fully legitimate outcome, not a fallback that's blocked.

## 25. Edit source annotation after watchlist decision

1. On a note that's already `complete` with at least one saved `Watchlist Review` decision (from test 24), go back to `Review Desk`, load one of that note's accepted entries, change something, **Attest & Save** (editing an accepted entry, deleting an entry, and saving a queue snapshot all trigger the same reopen behavior — `AttestSave`, `DeleteEntry` and `SaveQueueSnapshot` all call `ReopenNote`).
2. Check `Note Register`: `status` must revert from `complete` to `in_progress`.
3. Check `Watchlist Review`: **every** row for that `source_id` — including the one you saved as `complete` in test 24 — must now read `review_status` = `recheck`. This is unconditional; it doesn't check whether the decision was already `complete` first, so even a decision made minutes ago flips.

## 26. Actual tenant Copilot table write + AutoSave

This is the one test in the list that cannot be simulated by typing values yourself — it needs your actual M365 tenant Copilot.

1. With AutoSave **on**, open a note, follow `AI Instructions` verbatim (it's the embedded v2 prompt with exact cell addresses), and have Copilot draft into `AI Queue` / `AI Analysis Input` for real.
2. Confirm Copilot wrote into exactly the columns the v2 prompt specifies — `tInput` row 6 downward, no header row touched, no extra columns invented.
3. **Save queue snapshot** while AutoSave is actively saving in the background. Confirm no corruption — this is checking that `BeginWrite`'s `Application.EnableEvents = False` / `ScreenUpdating = False` guard and the recovery-copy mechanism hold up against a concurrent AutoSave cycle, not just against you clicking two buttons quickly yourself.
