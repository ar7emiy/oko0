GOKO v2 — architecture and data trace

Whole-note extraction, three detection lanes, claim assembly, category assignment, graph load. Every boundary payload shown in full.

One claim followed end to end. Claim 123456-789012-AB-01, notes 188213 and 188219. Dr. Monroe appears in both under different surface forms; a phone number and an NPI attach to him; an address appears with no determinable owner; and the same phone number later turns up in an unrelated claim, which is what creates the cross-claim path.

0 — Identifiers, occurrence layer, and node keys

Claim ids are structured, and the structure is load-bearing. Parsing it once at ingestion turns three separate lookups into graph edges, and gives cross-claim scoring the context it needs to avoid firing on every claim that shares an incident.

code

Parse, do not slice

Validate against the pattern and reject non-conforming ids. Positional slicing on a legacy id produces a silently wrong occurrence grouping.

pattern: ^[0-9]{6}-[0-9]{6}-[A-Z]{2}-[0-9]{2}$

{ "claim_id": "123456-789012-AB-01",
  "client_id": "123456",
  "occurrence_id": "123456-789012",
  "occurrence_seq": "789012",
  "coverage_code": "AB",
  "claim_seq": "01",
  "id_format_version": "1" }

rejected:
{ "raw": "123456-789012-ab-01", "action": "uppercase, accept" }
{ "raw": "LEGACY-4471902",      "action": "review_queue",
  "flag": "malformed_claim_id" }

Coverage code is uppercased at ingestion. Left mixed, ...-AB-01 and ...-ab-01 become two node keys for one claim, and every count downstream is wrong by an amount nobody notices.

code

Namespaced node keys

Note ids and watchlist ids are both bare integers in the same range. Namespacing prevents a mistyped MERGE from matching the wrong node.

note      188213  ->  "note:188213"
watchlist 440271  ->  "watchlist:440271"
client    123456  ->  "client:123456"
occurrence        ->  "occurrence:123456-789012"
claim             ->  "claim:123456-789012-AB-01"
detail            ->  "phone:+13125550101"

raw value kept as a separate property for display
and for joining back to source systems:
  (:Note {key: "note:188213", note_id: 188213})

Both id spaces span 99999 to 999999, so an unnamespaced 188213 is ambiguous between a note and a watchlist. In JSON that is survivable; in a graph MERGE it silently creates or matches the wrong node.

code

Relationship distance

The single most consequential addition. Two scores, computed separately, from the same shared-detail evidence.

distance(a, b):
  same_claim        -> handled by assembly, not here
  same_occurrence   -> identity_weight 1.00   suspicion_weight 0.00
  same_client       -> identity_weight 0.90   suspicion_weight 0.25
  different_client  -> identity_weight 0.85   suspicion_weight 1.00

{ "entity_a": "123456-789012-AB-01:E1",
  "entity_b": "123456-789012-CG-01:E2",
  "distance": "same_occurrence",
  "shared_details": ["phone:+13125550101"],
  "identity_score": 0.96,  "outcome": "same",
  "suspicion_score": 0.00,
  "note": "expected: one incident, multiple coverages" }

Two claims from one occurrence are one incident. The same claimant, adjuster, clinic and phone numbers appearing in both is structurally expected, so it is strong evidence of identity and no evidence of fraud. Scoring these together is what would otherwise make cross-claim alerts fire constantly on the least interesting pattern in the archive.

Occurrence is also a free blocking key and a retrieval level. Candidate pairs within an occurrence are cheap and high-yield for identity resolution. And because Occurrence is a real node rather than a string prefix, "show me everything about this incident" is one hop up from the claim rather than an indexed prefix scan. Ops works per claim by default; the occurrence view is the same dossier query one level higher.

1 — Note ingestion and three-lane extraction

One LLM call per note. Two deterministic lanes run alongside it: pattern matching with checksums for structured identifiers, and GLiNER for unpatterned name spans. Lanes reconcile before validation. The injection seam from GLiNER into the prompt is drawn but off by default — it lifts recall and destroys per-lane attribution, so it stays closed until each lane's contribution has been measured.

input

Raw note

Text exactly as stored. No preprocessing yet.

{ "note_id": 188213, "claim_id": "123456-789012-AB-01",
  "authored_at": "2026-03-17T09:42:00Z", "author": "adj_rlangford",
  "raw_len": 4980,
  "raw_text": "...clmt seen 3/14 by Dr. Monroe (NPI 1548392012).\r\n
     The treating physician noted decreased ROM.  He is reachable\r\n
     at (312) 555-0101 after 5 pm.  Office at 4410 N Broadway,\r\n
     Chicago IL 60640.  Referred to Lakeshore PT..." }

Note the CRLF line endings and doubled spaces — these are exactly what cleaning will alter, and therefore what the offset map has to account for.

code

Normalize and map offsets

Every edit is recorded as a translation entry. The raw text is never discarded.

{ "note_id": 188213, "clean_len": 4936,
  "policy_version": "clean-1.2",
  "edits": [
    { "raw_start": 48,   "raw_len": 2, "clean_len": 1, "kind": "crlf_to_lf" },
    { "raw_start": 131,  "raw_len": 2, "clean_len": 1, "kind": "collapse_ws" },
    { "raw_start": 1789, "raw_len": 2, "clean_len": 1, "kind": "crlf_to_lf" }
  ],
  "offset_map_fn": "clean_to_raw(clean_idx) -> raw_idx" }

clean_to_raw(1730) -> 1789

44 characters disappeared between raw and clean. Without this table every span in the system would point 44 characters off by the end of the note — silently, and only in the investigator's viewer.

code

Lane A — pattern scan and checksums

High recall on structured identifiers, zero ownership. Spans emitted natively.

{ "lane": "pattern", "patterns_version": "1.4", "note_id": 188213,
  "finds": [
    { "detail_type": "npi", "raw_value": "1548392012",
      "clean_span": [1204, 1214], "checksum": "pass" },
    { "detail_type": "phone", "raw_value": "(312) 555-0101",
      "clean_span": [1734, 1748], "checksum": "n/a" },
    { "detail_type": "address", "raw_value": "4410 N Broadway, Chicago IL 60640",
      "clean_span": [1802, 1835], "parser": "usaddress", "confidence": 0.93 },
    { "detail_type": "npi", "raw_value": "1548392018",
      "clean_span": [3301, 3311], "checksum": "FAIL_LUHN" }
  ] }

The last find is the case only this lane catches: a digit-transposed NPI that looks perfectly well-formed to an LLM. Checksum failure is a data-quality signal, not an extraction error — load it flagged rather than dropping it, since the note genuinely says that.

code

Lane B — GLiNER spans

Zero-shot, local, CPU. Covers unpatterned names that regex cannot reach.

{ "lane": "gliner", "model_version": "gliner_multi-v2.1",
  "labels": ["person", "organization", "vehicle"],
  "threshold": 0.60, "note_id": 188213,
  "finds": [
    { "label": "person", "text": "Dr. Monroe",
      "clean_span": [1190, 1200], "score": 0.91, "kept": true },
    { "label": "organization", "text": "Lakeshore PT",
      "clean_span": [1878, 1890], "score": 0.83, "kept": true },
    { "label": "organization", "text": "the shop",
      "clean_span": [2455, 2463], "score": 0.41, "kept": false }
  ] }

Spans are native, so GLiNER finds skip quote resolution entirely. The discarded low-score find is still logged — discard volume by label is how you tune the threshold against gold data rather than by guessing.

llm

Lane C — whole-note extraction

The only per-note LLM call. Emits verbatim quotes, never offsets. Coreference resolved in-context via occurrences.

{ "entity_mentions": [
    { "mention_id": "m1", "quote": "Dr. Monroe", "type": "person",
      "occurrences": ["The treating physician", "He"] },
    { "mention_id": "m2", "quote": "Referred to Lakeshore PT",
      "type": "organization", "occurrences": [] } ],
  "detail_mentions": [
    { "detail_id": "d1", "quote": "Dr. Monroe (NPI 1548392012)",
      "raw_value": "1548392012", "detail_type": "npi", "issuer": null,
      "owner_ref": "m1", "basis": "stated" },
    { "detail_id": "d2", "quote": "He is reachable at (312) 555-0101 after 5 pm",
      "raw_value": "(312) 555-0101", "detail_type": "phone", "issuer": null,
      "owner_ref": "m1", "basis": "inferred" },
    { "detail_id": "d3", "quote": "Office at 4410 N Broadway, Chicago IL 60640",
      "raw_value": "4410 N Broadway, Chicago IL 60640",
      "detail_type": "address", "issuer": null,
      "owner_ref": "UNASSIGNED", "basis": "stated" } ],
  "action_mentions": [
    { "action_id": "a1", "quote": "clmt seen 3/14 by Dr. Monroe",
      "action_type": "examined",
      "participants": [ { "mention_id": "m1", "role": "examiner" } ],
      "time_qualifier": "3/14", "stance": "asserted", "basis": "stated" } ] }

Three judgments here are the LLM earning its place. occurrences ties "He" to Dr. Monroe — no regex does that. d2 is marked inferred because ownership comes from the pronoun, not a direct statement. d3 is UNASSIGNED: the office plausibly belongs to Monroe, but the note does not say so, and proximity is not ownership.

code

Quote resolution

Exact find, then normalized retry, then fuzzy. Multi-hit disambiguates against the anchor mention.

m1  "Dr. Monroe"                     -> 1 hit  [1190, 1200]   ok
d1  "Dr. Monroe (NPI 1548392012)"    -> 1 hit  [1190, 1217]   ok
d2  "He is reachable at (312) ..."   -> 1 hit  [1719, 1762]   ok
d3  "Office at 4410 N Broadway, ..." -> 1 hit  [1793, 1835]   ok
a1  "clmt seen 3/14 by Dr. Monroe"   -> 1 hit  [1162, 1190]   ok

hypothetical multi-hit:
  quote "60640" -> 4 hits [1830, 2140, 2884, 3610]
  anchor: owner_ref m1 resolved at 1190
  distances: 640, 950, 1694, 2420  -> nearest 1830
  runner-up ratio 950/640 = 1.48  < 3.0 required
  -> REVIEW, not resolved

Every real quote here resolved on the first attempt because the schema instructs the model to quote a full phrase. The hypothetical shows why that instruction matters: a bare value in a note full of Chicago addresses is unresolvable, and the honest outcome is review rather than a plausible guess.

code

Round-trip check

Map to raw coordinates, slice the original, compare. The one test that validates the entire chain.

d2: clean_span [1719, 1762]
    clean_to_raw(1719) -> 1776 ; clean_to_raw(1762) -> 1821
    raw_text[1776:1821]
      == "He is reachable at (312) 555-0101 after 5 pm"   PASS

failure mode caught:
{ "detail_id": "d9", "quote": "billed under NPI 1548392099",
  "exact": 0, "normalized": 0, "fuzzy_best": 0.71,
  "verdict": "unverifiable_quote", "routed": "review_queue" }

One string comparison catches a hallucinated quote, an off-by-one in the offset map, a stale cleaning version, and a boundary bug. It is the reason a citation in the finished dossier can be trusted.

The fourth record is the recall gap this whole lane exists for: the LLM never emitted that NPI, and without the pattern scan it would be lost silently. code

Validation

Checks the schema could not express structurally. Separate layer, separate failure mode.

enum conformance
  detail_type in schema_v0_1.enum            -> pass
  stance in [asserted, denied, disputed, alleged]  -> pass
referential integrity
  a1.participants[0].mention_id == "m1" exists in this note  -> pass
  d1.owner_ref == "m1" exists                -> pass
format
  npi matches ^[0-9]{10}$                    -> pass
  phone normalizes to E.164                  -> pass

result: accept, 0 routed to review

Under constrained decoding, enum conformance should be structurally impossible to violate. It stays because it catches the case where the constraint was not actually in force — a version skew between call and validator, or a fallback to an unconstrained path. If it ever fires, something upstream is broken.

output

note_envelope

Everything stamped. Input to assembly.

{ "note_id": 188213, "claim_id": "123456-789012-AB-01",
  "versions": { "schema": "0.1", "model": "claude-sonnet-4-6",
                "gliner": "gliner_multi-v2.1", "patterns": "1.4",
                "clean_policy": "clean-1.2", "chunk_policy": "whole_note" },
  "entity_mentions": [ ... ], "detail_mentions": [ ... ],
  "action_mentions": [ ... ],
  "review_items": [
    { "flag": "checksum_fail", "detail_type": "npi",
      "raw_value": "1548392018", "clean_span": [3301, 3311] } ] }

chunk_policy is stamped even though it reads whole_note for every record today. When a long document forces the fallback path, or when the policy changes, the only way to tell a policy effect from a model regression is a version tag that was already there.

Oversized notes. Not drawn. Split on document structure first — dated entries, adjuster log records, section headers — fall back to sentence packing only inside an oversized structural unit, and overlap by whole sentences rather than characters. Segment results are rebased and overlap-deduplicated before rejoining at the parse step.

code

Blocking

Only mentions sharing a key are ever compared. This is what stops scoring from being quadratic.

{ "188213:m1": ["name_key:monroe", "name_key:monroe|dr",
                 "detail:npi:1548392012"],
  "188219:m4": ["name_key:monroe", "name_key:monroe|a",
                 "detail:npi:1548392012"],
  "188219:m1": ["name_key:lakeshore", "name_key:lakeshore_physical_therapy"] }

candidate pairs emitted: 1
{ "a": "188213:m1", "b": "188219:m4",
  "block_hit": ["name_key:monroe", "detail:npi:1548392012"] }

The shared NPI is doing the work here. Surname alone would also have blocked them together, but it is the identifier that makes the pair worth scoring rather than merely worth looking at.

code

Score and band

Mid band writes no edge. Under-merge is recoverable and visible; over-merge is a false attribution an investigator may act on.

{ "a": "188213:m1", "b": "188219:m4",
  "features": { "name_sim": 0.78, "detail_agree": 1.0,
                "detail_rarity": 0.97, "role_compat": 1.0,
                "type_match": true },
  "score": 0.94, "band": "high", "action": "write_edge" }

{ "a": "188219:m1", "b": "188221:m3",
  "features": { "name_sim": 0.74, "detail_agree": null,
                "detail_rarity": null, "role_compat": 1.0,
                "type_match": true },
  "score": 0.71, "band": "mid", "action": "flag_uncertain_merge" }

Name similarity is only 0.78 — "Dr. Monroe" against "A. Monroe, MD" is not a strong string match. The pair clears the high band on the strength of a rare shared identifier, which is exactly the weighting you want: identifiers should outvote names.

llm

UNASSIGNED retry

One batched call per claim, all unresolved details at once, with full-claim context. Optional in v1.

request:
{ "unassigned": [
    { "detail_id": "188213:d3", "detail_type": "address",
      "quote": "Office at 4410 N Broadway, Chicago IL 60640" } ],
  "entities": [
    { "entity_id": "123456-789012-AB-01:E1", "surface_forms": ["Dr. Monroe", "A. Monroe, MD"] },
    { "entity_id": "123456-789012-AB-01:E2", "surface_forms": ["Lakeshore Physical Therapy"] } ],
  "context_quotes": ["Lakeshore PT, 4410 N Broadway, billed 3/22"] }

response:
{ "188213:d3": { "owner": "123456-789012-AB-01:E2", "basis": "inferred",
                  "evidence_ids": ["EV22"] } }

Worth showing because the first guess would have been wrong. In isolation the office looks like Monroe's; a second note reveals the address belongs to Lakeshore. This is the payoff for refusing to guess at extraction time — UNASSIGNED stayed honest until evidence arrived.

exception

Contradiction detection

One entity, two values of a type that should be singular.

{ "entity_id": "123456-789012-AB-01:E1", "detail_type": "npi",
  "values": [
    { "normalized": "1548392012", "checksum": "pass",
      "detected_by": ["pattern", "llm"], "evidence": ["EV1", "EV14"] },
    { "normalized": "1548392018", "checksum": "FAIL_LUHN",
      "detected_by": ["pattern"], "evidence": ["EV31"] } ],
  "flag": "contradictory_singular_detail",

The checksum turns what would be an unresolvable conflict into an obvious one. Without Lane A this contradiction never surfaces, because the LLM emitted only the valid NPI and the transposed one was never seen at all.

      "participants": [ { "entity_id": "123456-789012-AB-01:E1", "role": "examiner" } ] } ] }
Transitivity. Union-find merges A and C when A–B and B–C both score high, even where A–C scored low directly. A low score is the absence of an edge, not a veto. The must_not_link band is what makes it one, and a cluster-size alarm catches what it misses.

Category call — E2

No rule fires: an organization with an address and no identifier. Only ambiguous entities reach the model.

{ "category": "medical",
  "subcategory": "physical_therapy_clinic",

code

Validate

Two checks with different meanings. One indicates a bug; the other indicates missing evidence.

"medical" in taxonomy_v3.enum              -> pass
"EV4"  in entity.evidence_ids              -> pass
"EV22" in entity.evidence_ids              -> pass
basis in [stated, inferred, rule]          -> pass
-> accept

contrasting failure:
{ "category": "medical", "evidence_ids": ["EV99"] }
  "EV99" not on this entity
  -> category = insufficient_evidence, flag = unresolved_evidence_citation

The evidence check is the one constrained decoding cannot perform, because valid ids are not known at generation time. A citation that does not resolve is the cheapest available detector for a fabricated justification.

exception

Three distinct outcomes

Never collapsed into one another.

  read the evidence, party is none of the five

{ "category": "insufficient_evidence", "basis": "llm" }

{ "error": "off_taxonomy_value", "returned": "orthopedic_supplier",
  "taxonomy_version_in_call": "3",
  "taxonomy_version_in_validator": "4" }

If an off-taxonomy return quietly became insufficient_evidence, a version-skew bug would appear in your evaluation as a recall problem and cost a week of looking in the wrong place.

Nothing enters the persistent store until the claim dossier is frozen, which keeps the scoreable artifact independent of the graph. Confirmed identity links project into canonical Person nodes without destroying the claim-scoped records beneath them.

Normalize and key

Only identity-bearing types become nodes. Everything else stays a property on the entity.

"(312) 555-0101"  -> "phone:+13125550101"
"312.555.0101"    -> "phone:+13125550101"
"1548392012"      -> "npi:1548392012"
"4410 N Broadway, Chicago IL 60640"
                  -> "address:4410 n broadway|chicago|il|60640"

not keyed:
{ "detail_type": "phone", "raw_value": "ext. 4471",
  "normalizes": false, "flag": "unnormalizable",
  "loaded": true, "keyed": false }

Unnormalizable values still load — the note says it, so the dossier records it — but they are never join keys. Keying on a fragment like an extension would manufacture paths between unrelated claims.

code

Upsert

Detail nodes are global and shared. Entity nodes are claim-scoped and never merged.

MERGE (d:Detail {key: "phone:+13125550101"})
  ON CREATE SET d.detail_type = "phone", d.first_seen = $now
SET d.raw_values_seen = apoc.coll.toSet(
      coalesce(d.raw_values_seen, []) + "(312) 555-0101")

MERGE (e:Entity {claim_id: "123456-789012-AB-01", entity_id: "E1"})
SET e.type = "person", e.category = "medical",
    e.subcategory = null, e.taxonomy_version = "3"

MERGE (e)-[r:HAS_DETAIL]->(d)
SET r.owner_status = "assigned", r.basis = "inferred",
    r.evidence = ["EV2"]

raw_values_seen accumulating on the Detail node is quietly useful: it is a running census of how one value is written across your archive, which is the evidence base for improving normalization rules.

code

Cross-claim path

Structural, not inferred. Normalization plus upsert-by-key created it.

MATCH (a:Entity)-[:HAS_DETAIL]->(d:Detail)<-[:HAS_DETAIL]-(b:Entity)
WHERE a.claim_id <> b.claim_id
RETURN a, b, collect(d.key) AS shared, count(d) AS n

result:
{ "a": "123456-789012-AB-01:E1", "b": "774100-220945-CG-01:E3",
  "shared": ["phone:+13125550101"], "n": 1 }

No model was asked whether these two claims are related. Two entities attached to the same node, and the path exists as a consequence.

A separate reviewable judgment layered on the structural path. Rarity-weighted.

  "distance": "different_client",
  "shared_details": ["phone:+13125550101"],

{ "shared_details": ["address:1100 w lawrence|chicago|il|60640"],
  "detail_rarity": 0.11,

Three cases, one query shape. Low name similarity with a rare shared identifier across different clients is worth an investigator's time, and is exactly what an automatic merge would erase. The same evidence inside one occurrence is near-conclusive for identity and worthless as a fraud signal. The third is a large building shared by dozens of unrelated parties — rarity is the only thing distinguishing it from the first.

Person projection

Derived state, recomputed from confirmed links. Never hand-edited.

{ "person_id": "P-0091",
  "canonical_name": "Monroe, Alan T.",
  "members": [ { "entity_id": "123456-789012-AB-01:E1", "claim_id": "123456-789012-AB-01" },
               { "entity_id": "774100-220945-CG-01:E3", "claim_id": "774100-220945-CG-01" } ],
  "union_details": ["npi:1548392012", "phone:+13125550101"],
  "derived_from_links": ["IL-00412"],
  "recomputed_at": "2026-09-18T02:14:00Z" }

(:Entity {claim_id:"123456-789012-AB-01", entity_id:"E1"})-[:RESOLVES_TO]->(:Person {person_id:"P-0091"})

Identity projects upward; assertions do not. Category, actions and evidence stay on the claim-scoped entity, because the same individual can be a provider in one claim and a witness in another. Undoing a bad merge means deleting one link and recomputing, not reconstructing what each claim said.

exception

Cluster-size alarm

Sits in front of watchlist matching so a blob entity never produces an alert.

{ "person_id": "P-1877", "member_count": 63,
  "threshold": 12,
  "chain_detail": "address:1100 w lawrence|chicago|il|60640",
  "detail_rarity": 0.11,
  "verdict": "implausible_cluster",
  "action": "suspend_projection", "routed": "review_queue" }

Transitivity bites harder across claims than within one. A clinic's main line or an apartment building will chain dozens of unrelated people into a single Person. The alarm suspends the projection rather than alerting on it, and names the detail that did the chaining so the fix is obvious.

Two things make this alert actionable rather than a bare name: a quote with raw-note coordinates an investigator's viewer can highlight, and identity_basis naming the link that joined the two claims — so if the merge was wrong, the alert is visibly wrong too. Below-threshold scores are stored so threshold behaviour is auditable rather than invisible.

Open items. The six-value taxonomy needs a written, versioned artifact. Detail normalization rules per type, and the list of identity-bearing detail types, are undecided. Rarity weights and the cluster-size threshold are unset placeholders. GLiNER should be gated on measured LLM entity recall — if recall is already adequate against gold data, the lane is infrastructure for nothing.
