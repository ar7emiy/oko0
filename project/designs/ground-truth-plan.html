Client onboarding · Track 1 of 2

Building the ground truth set on real claim notes

A six-week plan to produce a defensible, span-level ground-truth dataset from the client's unstructured notes, using their existing entity list as a location oracle and reserving expensive human reading for the one thing it cannot tell us: what everybody is already missing.

2 data scientists · 1–2 SMEs 3 sprints × 2 weeks Scope: ground truth only Excludes: system architecture, query-layer eval

01 What we have, and what each asset is actually worth

The client hands us three things, and they have very different evidential value. Getting this straight determines the entire cost structure of the build.

AssetTells usDoes not tell us
Entity name + note ID Identity, and that it appears somewhere in this note Where in the note. Nothing about entities not on the list.
Entity metadata (address, category/duty, ID citations) Additional attributes we can independently locate in the text Whether absence is real absence
Null metadata Where their pipeline gave up — a ready-made hard-case pool Whether the fact is in the text at all
The one asymmetry that shapes everything

Their entity list is a precision oracle, not a recall oracle. If a name is on it, it is almost certainly real — so we can trust it enough to auto-locate and only spot-check. If a name is absent from it, that tells us nothing, because incompleteness is the exact complaint that started this engagement.

So: use their list to make the known entities nearly free to label, and spend the entire human budget on the unknown ones. Any plan that spends SME hours re-confirming exact string matches is burning the budget in the wrong place.

The null-metadata pool is the fastest early win

Where their record has a null address but our extractor finds an address adjacent to that same entity in the note text, we have a concrete, checkable claim: your system dropped this and here is the sentence it is in. Verifying one of these takes an SME about five seconds. This costs almost nothing, needs no ground truth to be credible, and gives the engagement a visible result in week one — see ticket W1.

02 The dataset has three tiers, and they support different claims

The most common way ground-truth projects produce misleading numbers is treating partially-labelled documents as if they were complete. You cannot measure precision on a document where nobody looked at the unmarked text — every correct-but-unlabelled find becomes a phantom false positive, and tuning against it actively drives recall down. So completeness must be recorded per document, not assumed.

Gold
~150 notes · read cold

Exhaustively annotated by an SME with no pre-annotation shown. Every entity mention marked.

  • Supports recall and precision
  • Only tier that can audit the client's list
  • Source of the coverage estimate
Silver
~2,000 notes · auto-located

Client-list entities located in text by the matcher, with a certified per-tier error rate.

  • Supports recall against the known set
  • Supports ER cluster evaluation at scale
  • Cannot support precision
Unlabelled
remainder of corpus

No labels. Used for throughput, stability and distribution checks only.

  • Never appears in a quality metric
  • Feeds sampling frames
Why silver can be trusted at scale without verifying every span

We do not need a human to confirm every located span. We need to certify the locator: verify a random sample per match tier (exact / normalized / fuzzy / surname-only), establish an error rate for each tier with a confidence interval, then apply the locator in bulk with that error rate stated. Sampling to certify the tool replaces reviewing its every output, and it is the single biggest time saving in this plan.

Output format: the existing manifest schema, unchanged

The frozen ground-truth set is emitted in the same schema_version: 2 manifest shape the synthetic corpus already uses. That means audit.py, qa_viewer.py and ablation.py run against real client data with no modification — the stratified recall breakdowns, the B³ threshold sweep, the overlay viewer, all of it works on day one. The synthetic corpus does not get retired; it becomes the regression suite we tune against without spending SME hours.

03 How big, and how we know

Gold sizing is driven by the confidence interval we want on recall, per stratum — not by a round number of documents.

recall ≈ 0.85, target ±5% at 95% confidence → n ≈ 1.96² × 0.85 × 0.15 / 0.05² ≈ 196 entity instances per stratum → × 1.5 design effect (mentions cluster within a note) ≈ 300 instances per stratum → ÷ ~15 entity mentions per note ≈ 20 notes per stratum → × 5 strata ≈ 100 notes → + 30 dual-annotated calibration notes → + headroom ≈ 150 gold notes

Strata are drawn on note category (medical / legal / SIU / payment / general), which is where extraction behaviour actually differs. A single blended number hides the thing the client needs: which kind of note we handle badly.

04 What the SME actually does, and in what form

Five task types, each with a fixed, closed response vocabulary. Nothing is free-text except the optional note field, because free-text judgements cannot be aggregated into a metric. Everything is recorded through the QA viewer, not in spreadsheets — spans typed by hand into a sheet drift from the text and cannot be re-verified.

TaskSME seesSME recordsFeeds
T1 · Cold annotation Note text only. No pre-marks, no client list. Span boundary + entity class + certainty (certain / probable) ; mark doc complete when done Gold tier, coverage estimate
T2 · Located-span verify One pre-located span highlighted in context correct / wrong span / not this entity, + boundary fix if wrong Locator certification
T3 · Not-found triage Entity name from client list + full note text found here (mark span) / not textually present / referenced without a name Matcher gap analysis
T4 · Null-metadata recovery Candidate identifier our extractor found + the entity it may belong to belongs / does not belong / unsure Week-1 gap demo, identifier GT
T5 · Adjudication Two annotators' conflicting spans side by side Pick A / pick B / neither / both Gold tier, guideline revision
Two protocol rules that protect the recall goal

Certainty is three-tier, not binary. certain / probable / not-marked. Metrics get reported bracketed — strict (certain only) and lenient (certain + probable). The width of that bracket is itself a finding, and it stops genuinely ambiguous mentions from being silently scored against the system.

A false positive is presumed to be a ground-truth gap until an SME says otherwise. When the system finds something gold does not have, it routes to T2 before it counts against precision. Skipping this is how a recall-biased product ends up tuned for recall loss.

Guidelines must exist before anyone annotates

The boundary questions have to be settled once, in writing, with worked examples: do we include titles (Dr. Smith), suffixes (Jr.), possessives (Jones's), org suffixes (LLC)? Are role-only references (the adjuster) entities? Do duplicated mentions in quoted email chains get marked? Each unsettled question becomes pure noise in the final number. Ticket D1, and it is a hard dependency of every annotation ticket.

Where this slips, if it slips

D2's κ gate. If the first calibration round misses 0.75, the fix is a guidelines revision and a re-run — roughly a week. That is the intended behaviour, not a failure: shipping a gold set built on annotators who disagree produces a number nobody can defend. Budget for one re-run and treat a clean first pass as upside.

E2. If span marking is not fast, gold annotation stretches from days into weeks. It is the highest-leverage engineering ticket in the plan and should not be deferred to sprint 2.

07 Decisions needed before sprint 1 opens

Each of these changes ticket content. They are cheap to answer now and expensive to answer after annotation has started.

  1. Is a role-only reference an entity? "The adjuster confirmed…" with no name. Recommend: yes, marked as a distinct class — coreference needs it, and excluding it hides a real category of miss.
  2. Do quoted/forwarded email duplicates get annotated? Recommend: yes, flagged as quoted, so they can be included or excluded from a metric after the fact rather than being unrecoverable.
  3. Boundary conventions for titles, suffixes, possessives, org suffixes. Any answer works; no answer is fatal.
  4. Does the client's category/duty field become part of ground truth, or context only? If it is ground truth, role classification becomes a measurable task and adds an SME response field.
  5. How many SMEs are actually available? With one, IAA has to come from a DS acting as second annotator on the calibration set — weaker, since a DS lacks the domain judgement, but far better than no agreement measurement at all.

08 What this dataset will not be able to tell us

Stated plainly now so it does not have to be explained defensively later.

  • Precision anywhere but gold. Silver notes are not exhaustively read; a system find outside the located set is unjudged, not wrong.
  • Anything above the IAA ceiling. If two SMEs agree at 0.88, a system scoring 0.92 against them is measuring annotation noise. Every metric is reported against that ceiling.
  • Entities nobody found. The capture–recapture estimate bounds this, it does not eliminate it. The bound is reported with the number.
  • Whether the client's list was right. We treat it as a precision oracle by assumption. Gold is the only tier that tests that assumption, on ~150 notes.
