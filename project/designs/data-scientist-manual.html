Ground truth build · engineering reference

Data scientist manual

What actually happens at each stage of building ground truth on real client data, and which file is responsible for it. This isn't a run-book of commands — the point is that you understand the process well enough to change the logic, swap a matching strategy, or debug a bad result, not just execute a script.

01 Freeze and fingerprint the notes

Before anything reads a note's contents, lock down the note's identity.

1
Freeze + hash
new

Every span anyone ever records — a system's or a human's — is a (note_id, char_start, char_end) triple. That position is only meaningful if the note's text can never silently change underneath it. This stage assigns/confirms a stable ID per note and computes a checksum of its exact byte content, so any later change is detected, not silently absorbed.

src/hashing.py
Already does exactly this for the synthetic corpus — reuse the pattern directly.
sha256_file(path) — hash one file · write_hashes() / verify_hashes(stage) — write and re-check a corpus-wide manifest
new: scripts/freeze_client_notes.py
Point hashing.py's functions at the client's raw note directory instead of data/raw_notes/. Small glue script, not new logic.

02 Ingest the client's entity spreadsheet

2
Parse and normalize the client file
new

The client's file has two independent sources per claim: an exact-string search (exact_string_bolo_search_matched_entity_name + bar-delimited note IDs) and a GenAI match (genai_matched_entity_record, double-bar-delimited: name/address/city/state/zip/phone/email/ner-tag, + genai_matched_note_ids). Parse both into one flat table: one row per (entity, note_id, source). Note which fields are blank per entity — that blank-field list is what stage 3's null-metadata pass runs against.

new: scripts/ingest_client_entities.py
Splits the delimited columns, flattens to one row per (entity, note_id), flags blank fields per entity. Straightforward parsing, no modeling.

03 Locate known entities in the note text

3
The locator
new

The client's file tells us which note an entity is supposedly in. It never gives a character position. This stage converts "Robert Miller is somewhere in note #4471" into an exact offset.

Two paths, because the two sources behave differently:

  • Exact-search entities — trivial. The client already told us the string is a literal match in a specific note; find it with a plain substring search against that note's frozen text. No fuzzy logic needed here.
  • GenAI-matched entities — not guaranteed literal. The record may be normalized or reformatted relative to how it actually reads in the note (name-order flips, nicknames, differently-formatted addresses/phones). This path needs real matching logic.
src/textnorm.py
Built for exactly this. Don't re-derive it.
normalize_name(), are_nickname_variants(), soundex(), jaro_winkler() / token_set_jw() — name matching under flips/nicknames/typos · phone_last7(), address_key(), normalize_email(), normalize_identifier(kind, value) — identifier normalization for matching client-format values against note text
new: scripts/locate_entities.py
Orchestrates: for each entity, try exact match first, fall back to normalized/fuzzy match via textnorm.py against the note text named in genai_matched_note_ids. Emits (entity, note_id, char_start, char_end, match_tier).
This is not entity_resolution.py

src/entity_resolution.py resolves our own extracted mentions against each other (mention-to-mention, via Splink). This stage is different: matching a known name string against raw text to find its position. Don't conflate the two — they solve different problems and the locator has to exist before entity resolution is even relevant here.

04 Run our extraction pipeline on real notes

4
Extraction, pointed at new input
adapt

This is the actual system under evaluation. It has only ever run against our synthetic corpus. Running it on real notes for the first time is itself a validation step — expect to find and fix real surprises, not just execute a known-good command.

src/pipeline_v2.py
Orchestrates the extraction pass: builds mentions, identifier observations, coref links from raw note text.
_is_plausible_name(surface) — the name-shape filter (currently requires ≥2 capitalized tokens). This is the single most likely thing to need adjusting for real phrasing — it's already a known limitation on the synthetic corpus too (misses bare surnames).
src/ner_ensemble.py
The token-level name/org pattern matcher and its noise/stopword lists.
DeterministicTokenNER — the regex patterns (_RE_SEQ, _RE_FLIP, _RE_TITLED, _RE_INITIAL) and the _LEADING_NOISE / _STOP word lists. Real client notes will use different sentence-opener verbs and structural boilerplate than the synthetic generator produced — expect to extend these lists from what silver-pass triage turns up.
src/gazetteers.py
Identifier pattern matchers (phone/email/address/NPI/etc.) and role-from-context inference.
Expect to tune here, not just run

If extraction looks obviously wrong on real notes (missing an entire category of mention, or over-firing on boilerplate), this is the stage to fix — not a sign the whole approach is broken. The synthetic-corpus numbers in ARCHITECTURE.md are a lower bound, not a guarantee, on unfamiliar real-world phrasing.

05 Compare: system output vs. located ground truth

5
Overlap-based scoring
reuse

Once stage 3 has produced located spans and stage 4 has produced the system's own spans, scoring is comparing two sets of (char_start, char_end) ranges for overlap — found / missed / extra. This logic already exists and doesn't change for real data, because it was written against the manifest shape, not against anything synthetic-specific.

src/audit.py
The scoring engine. Works unmodified once ground truth exists in the same manifest shape (stage 8).
_overlaps(s1,e1,s2,e2) — the core span-overlap test · entity_recall() / entity_precision() — found/missed/extra classification, broken out by hard-case tags · identifier_recall() — same, for identifiers, orphan vs. named broken out separately

06 Entity resolution on real mentions

6
Clustering mentions into entities
reuse

Once real mentions exist (from stage 4), the same probabilistic resolver clusters them into entities, exactly as it does for the synthetic corpus. The comparisons (name, email, phone, address, etc.) are generic — they don't assume synthetic data.

src/entity_resolution.py
SplinkResolver.resolve() — trains and scores match probabilities · comparison_specs() / comparison_level_labels() — the field comparisons and their human-readable levels · cluster_at(edges, mention_ids, threshold) — connected components at a chosen threshold · run() — orchestrates end to end, saves the trained model to store/splink_model.json
The operating threshold needs re-checking

CFG.ER_LINK_THRESHOLD = 0.45 was chosen from the synthetic corpus's B³ curve. Real-data name distributions (common surnames, real address formats) will shift that curve — re-run the threshold sweep against real ground truth once it exists rather than assuming 0.45 still holds.

07 The correction loop

7
Fixing ground truth without breaking reproducibility
reuse

When an annotator flags a wrong span or a wrong entity, that correction never edits the frozen ground truth file directly — it's appended to a separate patch file, applied on read. This is what lets you fix mistakes without invalidating everything built on the sealed data.

src/audit.py
_load_manifest() — loads the sealed file, then applies patches · _apply_corrections(manifest) — merges data/gt_corrections.json on top, matching by (doc_id, span)
src/qa_viewer.py
The review tool — used after ground truth exists, to audit the system's output against it and queue corrections. Not part of creating ground truth itself.
queue_correction() — writes one correction · doc_overlay() / render_doc_overlay_html() — the found/missed/extra visual per document

08 Assemble and freeze the manifest

8
One shared shape for silver and gold
new

Silver output (stage 3, human-verified) and gold output (the SME's cold reads) both get written into the same manifest shape the synthetic corpus already uses — placements (entity/identifier/event spans), entities, coref_chains. This is a schema to match, not code to reuse — real ground truth doesn't run corpus_gen.py, it just writes to the shape that module documents. Tag every placement with its tier (silver / gold) and match method, so downstream reporting can separate them.

src/corpus_gen.py
Reference only — read _entity_manifest() and the final manifest = {...} assembly for the exact field names to match, not to execute.
src/contracts.py
GROUND_TRUTH_MANIFEST_SHAPE — the documented shape, and the authority for field names if corpus_gen.py and this manual ever disagree.

09 Audit and report

9
The numbers that go to the client
reuse

Once the manifest exists, every metric in this project's evaluation layer runs against it unmodified — recall/precision stratified by category and hard-case, identifier recall, the entity-resolution B³ threshold sweep.

src/audit.py
run() — full audit, everything below · bcubed_sweep() — cluster quality across resolution thresholds · coverage_check() — hygiene check only, not a quality metric
Report by tier, not just overall

Silver-derived and gold-derived numbers answer different questions (§01 of the annotator manual). Keep them separate in any report — collapsing them into one blended number hides which claim you can actually defend.
