Will this line classifier generalize?

It is worth being blunt about what _classify_line actually is: five regexes over one line at a time, plus one stateful flag. There is no model here. On the synthetic corpus it scores well, but that is a closed loop — our own generator writes the very markers the classifier looks for. Three specific places it is likely to behave differently on real client notes:

rulewhat breaks on real notesconsequence
SIG_MARK_RE = ^\s*--\s*$
signature delimiter		 This is the Usenet/mailing-list convention. Outlook and Exchange almost never emit a bare -- line; real signatures start with “Thanks,” or a name. Worse, in_sig is a one-way latch — set once, never cleared. The likely failure is not a missed signature but the opposite: one stray -- divider turns every remaining line in the note into email_signature. That is a bug, not just a tuning gap.
BOILER_RE
3 hardcoded phrases		 Matches only “CONFIDENTIALITY NOTICE”, “intended recipient”, “privileged”. Real disclaimers vary by carrier, firm, and jurisdiction. A disclaimer worded differently is never excluded, so the names inside it reach the name filter and become mentions. Precision loss, and it looks like an extraction error rather than a segmentation one.
LABEL_RE
leading “Word:”		 Fires on any line beginning with a short token then a colon — including ordinary narrative openers: Update: spoke with counsel, Status: pending, Per adjuster: no coverage. Prose gets typed template_block. Mostly harmless today (a single line will not reach TEMPLATE_MIN_LABELS and so will not fingerprint), but it makes any “how much of this corpus is template?” measurement read high.

The reason this matters more than it looks: the label is not advisory. pipeline_v2 reads boilerplate ranges straight from this table and drops name candidates inside them (n_dropped_boiler). So a missed disclaimer costs precision, and a false-positive boilerplate segment silently deletes real names with no trace in the output.

Honest answer to “will it generalize?” — the email-header rule will, because From:/Sent:/To:/Subject: is a near-invariant of text-rendered mail. The label-colon rule will, roughly. The signature latch and the boilerplate whitelist will not, and the latch can fail catastrophically rather than gracefully. The fix is not longer regexes: it is (1) clear the latch at a blank line or a new header block, (2) score boilerplate on disclaimer-like features rather than three literal phrases, and (3) make the label advisory — never let a segment kind be the sole reason a candidate is dropped, so a classifier mistake degrades ranking instead of erasing evidence. Which of these actually bite is measurable the moment we have real notes in hand, and that measurement belongs in the ground-truth track.

D3 Filter, classify, bind, and persist

single goal of this blockTurn the surviving candidates into typed, span-grounded database rows — separating name handling from identifier handling, since they follow genuinely different rules.

Worked data example — what "evidence span" means

data going indata coming outwhat happened
subject: mention m0000153 ("Robert Miller", chars 40–52)
identifier candidate: "(312) 555-0148", chars 918–932, bound via subject_for()		Assertion{subject_mention_id:"m0000153", predicate:"has_phone", object_value_norm:"3125550148", source_span_start:918, source_span_end:932}The assertion's subject points at the name's location; its evidence span (source_span_start/end) points at the phone number's location — a different place in the text. That gap is exactly why evidence span is its own field: the fact is ABOUT the subject, but PROVEN at the evidence span, and the two are not always the same characters.

What "resolving anaphora to antecedent mentions" means

An antecedent is the earlier word or phrase a later reference points back to. An anaphor is that later reference itself — a pronoun, or a descriptor like "the claimant." Coreference resolution is the activity of finding, for every anaphor, which antecedent it points at.

John gave Mary a present. She loved it.
anaphorantecedentrelationship
"She""Mary"pronoun refers back to the person named earlier
"it""a present"pronoun refers back to the object named earlier

The same pattern inside a claim note

— What entity_class is for, and whether it's the right shape

what's actually being classified A per-mention label — not a per-entity one, so it can legitimately vary across mentions of the same real person — set once by _classify() in Fig D3, from surface-intrinsic signals first (org suffixes, "Dr."), then context on either side (an internal carrier domain, an external firm name, a "Clmt Atty —" template cue).

Today it's a closed five-value set: claimant, attorney, medical_provider, repair_shop, adjuster. It does two jobs that deserve different answers.

Person vs. organization is genuinely binary and load-bearing — entity resolution's cannot_link_reason() uses exactly this distinction to refuse merging a person into a repair shop. A closed set is correct here because there are only ever two real values.

Role in the claim is a different question wearing the same field, and it's the same restrictive-box mistake the predicate whitelist was earlier in this project — closed to five roles when a real claim has witnesses, employers, landlords, public adjusters, SIU investigators, family members, opposing counsel. It's not hypothetical: the code's own fallback is LABEL_TO_CLASS.get(label, "claimant") — a generic "person" mention that matches none of the specific signals is silently labeled claimant by default, and a generic "organization" is silently labeled medical_provider. That's not a missing bucket, it's an active mislabel.

The fix is the same shape as the predicate fix: split the field. entity_type: person | organization stays closed and keeps doing resolution's structural job. role becomes open vocabulary — a short common list for filtering convenience, normalized toward canonical forms, with no default fallback: an unmatched mention gets role: null, not a guess dressed up as a fact.
