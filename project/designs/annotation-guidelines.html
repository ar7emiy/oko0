01 The two kinds of work, and the order

You'll do two different kinds of task. Both matter, but they're not interchangeable, and the order is deliberate.

Silver work comes first. The client already gave us a spreadsheet of entities they believe are in each claim, found two ways: an exact-text search, and a separate AI-based match that includes address, phone, and email where it could find them. You're not finding these entities — a script already located most of them in the note text. You're checking the script's work and chasing down the parts it couldn't do automatically. Three tasks, below (§02–§04). Fast, and it covers a lot of notes quickly.

Gold work comes after. You read a note with nothing shown to you at all — no list, no hints — and mark everything yourself. Slower, and only done on a smaller set of notes, because it's the only way to find entities that nobody's process — not the client's, not ours — ever flagged. See §05.

Why the order matters

Doing silver first means the odd cases in the client's real data — the address format that's formatted strangely, the name spelled three ways — show up and get written into this document before you do the harder, less-checked gold reading. If you hit something confusing during silver work, say so — it likely becomes a rule here before gold starts.

The "notice anything else?" box

Every silver row — all three tasks below — ends in one more field: a spot to jot down anything else you happen to see nearby while you're already reading that sentence for another reason. You'll often have to read the surrounding context anyway to judge the thing you were actually sent to check — if a second entity is sitting right there and nobody flagged it, write it down. It costs you nothing extra and it's a real find.

This is a bonus, not a reading assignment

Writing something in this box does not mean you read the whole note — you were still only looking at the part you were shown. So it never marks a note complete, and it's kept separate from gold in how it's counted later: it's good evidence that something is really there, but it can't be used to say "and nothing else was missed in this note," because you weren't asked to check for that. Only a full cold read (§05) earns that claim. Write it down anyway — it's not wasted, it's just counted honestly.

02 Silver task A — locate-verify

What you'll see

a spreadsheet row + the note text next to it
col 1Claim number and note ID
col 2An entity name (from the client's exact-text search or their AI match)
col 3The sentence from the note, with the spot our script found already marked in brackets
...spoke with Robert Miller regarding the POA update...

What you do: read the bracketed sentence. Is the bracket in the right place, and is it actually this entity?

You answer one of: correct · wrong span (drag the correction) · not this entity (it's a different person/org with a similar name).
+ optional: notice anything else nearby? see §01

A few seconds per row. You are not re-reading the whole note — just the one sentence you're shown.

03 Silver task B — not-found triage

What you'll see

an entity name our script could not find in the text, and the full note
col 1Claim number, note ID
col 2The entity name from the client's list
col 3The complete note text — this time you search it yourself

What you do: read the note and look for this person or organization. They might be there under a nickname, an initial, a misspelling, or referred to without a name at all ("the claimant's daughter"). Or they might genuinely not be mentioned in this note's text — only in the client's records.

You answer one of: found here (mark the span) · referenced without a name · not textually present.
+ optional: notice anything else nearby? see §01
Why this bucket exists

An exact-text search only catches literal matches. Everything in this task is a case that kind of search was always going to miss — that's not a flaw in the client's process, it's exactly the gap this whole project is measuring.

04 Silver task C — null-metadata recovery

What you'll see

an entity with a blank field, and a candidate value found nearby in the text
col 1Entity name, and which field is blank in the client's record (phone / address / email)
col 2A candidate value our extraction found in the same note, near this entity
col 3The sentence it came from, in context
...callback left at (312) 555-0148, ask for Robert...

What you do: read the sentence. Does this value actually belong to this entity?

You answer one of: belongs · does not belong · unsure.
+ optional: notice anything else nearby? see §01

This is the most valuable task in the whole exercise — a confirmed row here is direct, provable evidence of something the client's own process missed.

05 Gold — the cold read

What you'll see

a blank note. nothing marked, nothing listed
1Open the assigned note. No highlights, no candidate list, no hints.
2Read the whole thing once for context.
3Go through it and record every person, organization, phone, email, and address you see — see §06–§09 for exactly what counts and where the boundary goes.
4When you reach the end, mark the note complete. Only do this if you're confident you read every line carefully — see the warning in §10.
5Only after step 4 — the client's known entities for this note are revealed to you. Reconcile: check off the ones you already caught, add any you missed, flag any the locator got wrong.
Why step 5 comes after, never before

Seeing the client's list before you read pulls your attention toward confirming what's already flagged, and away from noticing what isn't. That silently defeats the entire purpose of this task, which is finding what nobody flagged. Steps 1–4 have to happen with nothing shown to you.

You record, per entity: a span (drag or type the exact phrase), an entity type, and a certainty (§08).

06 Is this an entity? — the decision tree

Applies to everything you mark, silver or gold — every party, not just the claimant and their attorney.

Does this refer to a specific person or organization — not a category?
No → skip"the adjuster's office," "our legal team" as a generic group
Yes → continuea specific name, or a role clearly pointing at one person
Is it named directly (a proper name, "Dr. ___," a firm name)?
Yes → mark, certain"Robert Miller," "Alicia Reyes, MD," "Whitfield Trial Group"
No → continuea pronoun, a role-only phrase, a descriptor
Does a role-only phrase point at exactly one person in context ("the adjuster," "her attorney")?
Yes → mark, probableunless the note makes it unambiguous, then certain
No → skiptoo vague to attribute to one entity

Worked example

Spoke with Robert Miller regarding the POA update. He confirmed the treating provider remains Alicia Reyes, MD at the Lakeshore clinic. Claimant's attorney continues to be D. Alvarez, Esq. of Whitfield Trial Group.
greennamed directly — mark certain
amberpronoun/role, one clear referent — mark probable
strucka place, not an entity — do not mark
Identifiers are their own mark

A phone number, email, mailing address, or ID number gets marked separately, even next to a name — don't fold it into the name span. And mark an identifier even when no name is anywhere nearby: "Callback left at (312) 555-0148, no name given" — mark the phone number on its own. This is the exact case identifier-first extraction exists to catch, so it's the one most worth getting right.

07 Boundary rules

Where exactly a mark starts and ends.

includeTitles: Dr. Reyes, not split apart.
includeSuffixes: Robert Miller Jr. — one mark, not two people.
includeOrg suffixes: Whitfield Trial Group LLC — the legal suffix stays in.
excludePossessive 's: mark Robert Miller's policy, not Robert Miller's.
mark, probableRole-only with no name: the treating physician ordered an MRI.
mark every occurrenceQuoted/forwarded email chains: mark all repeats, flagged quoted.
excludeSentence-initial verbs: "Contacted James Moore" — the mark is James Moore only.
The most common real mistake

Swallowing a sentence-opening word into the name because both are capitalized. Read the sentence, not just the capital letters.

08 Certainty: certain vs. probable

Every mark you make — silver or gold — carries one of two tiers. Not a hedge; it's what keeps a genuinely ambiguous mention from being scored as if it were obvious.

certain You'd stake your judgment on it without hesitation.
probable You believe it, but a reasonable second reader might mark it differently.

Every metric built from this data gets reported twice — strict (certain only) and lenient (certain + probable). Neither is "the real one."

09 Hard-case tags

Attach any that apply while marking — don't hunt for them.

jr_srJr/Sr suffix conflict at the same address.
shared_addressTwo distinct entities share one address.
recycled_phoneA phone number that seems to have moved between entities.
address_changeThis entity's address changed between notes.
identifier_reassignedAn identifier appears to have moved between entities.
high_fanoutRecurs across an unusual number of claims (attorney, provider).
phoenix_shopA repair shop that appears reopened under a new name at an old address.

10 Common mistakes

  • Marking a gold note complete after skimming it. If you're not sure you read every line, leave it in progress. A falsely-complete note quietly corrupts precision.
  • Revealing the client's list before finishing the cold read (§05). Defeats the purpose of gold entirely.
  • Splitting one mention into two marks — title or suffix separated from the name (§07).
  • Treating "certain" as the default. Ask: would a second reader agree without discussion? If not, probable.
  • Skipping identifiers with no name attached. The highest-value case in the whole dataset (§06).

11 Quick reference

Cheat sheet

Task order
  • Silver first: locate-verify → not-found triage → null-metadata recovery
  • Gold second, and always blind-first, reveal-second within a note
Mark it
  • Named person or org → certain
  • Role/pronoun with one clear referent → probable
  • Any phone / email / address / ID → its own mark, even with no name nearby
Don't mark it
  • A place, not a person or org
  • A generic category
  • Sentence-opening verbs swallowed into a name
When unsure
  • Mark probable, never skip, never guess certain
  • Note it — becomes a rule for everyone next revision
